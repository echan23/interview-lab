The Project: InterviewLab

A shared in-browser code editor for running mock coding interviews. Live at interviewlab.dev — create a room, send the link, start coding.

Features

  • Real-time edits — everyone in a room sees keystrokes as they happen
  • Sharing via URL — no accounts, no setup
  • In-browser code execution — Python, Java, C++, JavaScript, Go
  • AI-generated feedback — hints on your code, generated questions
  • Cross-node writes on a document — two users on different servers still edit the same document consistently

Why

Existing tools were either laggy (Codefile.io) or paid (CoderPad). I wanted a free tool that felt instant.

Goal

Three hard requirements drove the whole design:

  1. Editing must feel local. Remote keystrokes should render fast enough that two people can talk and type over each other naturally.
  2. Untrusted code must run safely. The core feature is literally executing strangers' code on my server.
  3. State must survive scale-out. A room has to work identically whether its users land on the same backend instance or different ones.

Everything that follows is in service of these three.

Concurrency: One Goroutine Owns Each Room

   register/unregister --\
   edits (broadcast) -----\        +---------------------+
   stopwatch events -------+-----> |     Room.Run()      |
   question edits ---------/       |  single select loop |
   Redis subscribe -------/        |  owns room content  |
                                   +----------+----------+
                                              |
                              +---------------+--------------+
                              v                              v
                       Redis write / 2s               DB flush / 10s
  • All mutations flow through channels into one select loop per room
  • The document string is touched by exactly one goroutine — the hot edit path needs no locks
  • Durability runs on background timers, never blocking an edit
  • One context.Cancel() tears down every routine on shutdown
  • Trade-off: a slow consumer can stall the loop; per-client channels bound the damage

Three Tiers of State

TierHoldsWritesLifetime
Memory (Go)Live document, authoritativeEvery editWhile room runs
RedisContent hash, pub/subEvery 2 s5-minute TTL
PostgresDurable snapshot (UPSERT)Every 10 sForever
  • Edits mutate memory instantly; durability happens on timers
  • Rooms empty for 5 minutes flush and shut down; Redis TTL garbage-collects the rest — idle cost is ~zero
  • Rejoining a dead room: Redis miss → read Postgres → rehydrate. Nothing is lost.

                                                    X  no public port
  • Mistake I made first: the frontend called Piston directly on a public port 2000 — anyone could POST arbitrary code to the box, bypassing every app-level limit
  • Fix I owned: route /api/execute through the Go backend; bind Piston to the internal Docker network only
  • Defense in depth: reCAPTCHA on room creation, 100-line editor cap, rate limit on the AI tier

Hardest Problem: Scaling Past One Server

The wall: room state lived in one server's memory. Two users behind a load balancer could land on different instances — same room URL, two disconnected documents.

Options considered

OptionScalesSimpleRobustVerdict
Sticky sessionsNoYesDies on redeployRejected
Full CRDT (Yjs/Automerge)YesNo, heavyYesRejected
Redis relay + offset editsYesMostlyYesChosen
  • Each server keeps its own in-memory copy; edits relay through a per-room Redis channel
  • The Redis hash is the shared source of truth for joins/reconnects
  • CRDT rejected as overkill for 2–3 person rooms — this is what makes cross-node writes on one document work at the right cost

Two Bugs the Relay Created

Bug 1: Echo loop

  • A server publishes an edit, then its own subscriber delivers it right back — every cross-server keystroke doubled
  • Fix: stamp each envelope with Origin = ServerID; subscribers drop their own messages. Same idea client-side with a sender ID.

Bug 2: Offset drift

  • Monaco emits multi-range diffs; applying them left-to-right shifts later offsets and corrupts the document
  • Fix: sort each batch by RangeOffset descending before splicing, so earlier edits never move offsets not yet applied. Bounds-check every splice.

Honest limitation

Last-writer-wins on ranges, not a CRDT. Two users editing the exact same span simultaneously can conflict — acceptable at interview scale, and I know precisely where it breaks.

Batching the Cross-Server Relay

Problem: publishing every keystroke to Redis = one network round trip per character.

Solution: per-room publish batcher — flush at 20 edits or 200 ms, whichever comes first.

 Redis publishes per 100 keystrokes

 per-edit  |████████████████████████████████████████|  100
 batched   |██|                                          ~6
  • Local peers still see edits instantly; only the cross-server path is batched
  • 200 ms sits below the threshold where remote typing feels laggy
  • Separate cadences: 200 ms relay, 2 s Redis hash, 10 s Postgres — each consistency need pays only its own cost

AI Feedback Tier and Deployment

AI feedback

  • FastAPI on AWS Lambda — scales to zero, isolated from the stateful core
  • Proxied through the Go backend so API keys never reach the browser
  • Round-robin key rotation on rate limits; global limiter caps spend

Deployment

 git push main -> GitHub Actions -> SSH to EC2
              -> docker compose up --build
              -> install missing Piston runtimes (idempotent)
              -> /healthz checks Redis -> live

Decisions I'd Defend — and Q&A

  • Actor-per-room concurrency — lock-free hot path, clean shutdown. Would choose again.
  • Redis relay over CRDT — right-sized to the product; horizontal scale at a fraction of the complexity.
  • Proxying the sandbox — found and closed my own security hole; untrusted execution never faces the internet.
  • What I'd do differently — start with the origin-stamped relay and offset-sorted edits on day one, and build the deploy pipeline first. A redo would take roughly half the time.
